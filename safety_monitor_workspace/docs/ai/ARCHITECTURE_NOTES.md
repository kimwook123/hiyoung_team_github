# ARCHITECTURE_NOTES.md

## 현재 목표 구조

- `Client`
  - 영상 소스 소유
  - 로컬 객체 탐지 수행
  - 소스별 룰 옵션 설정
  - 서버로 상태, 프리뷰, 프레임 탐지 결과, 이벤트 클립 전송
- `Server`
  - 소스 메타데이터 저장
  - 소스 상태 저장
  - 프레임 탐지 결과 저장
  - 소스별 룰 적용 후 이벤트 판정 및 DB 저장
  - 프리뷰 스트림, 이벤트, 상태, 클립 조회 API 제공
- `Viewer`
  - 서버 데이터 조회 전용
  - 프리뷰 스트림, 이벤트, 상태, 클립 표시

## 현재 실제 분리 상태

### 서버

- FastAPI 앱: `safety_monitor_server/`
- 중앙 저장소:
  - `data/monitor.db`
  - `data/clips/`
  - `data/source_cache/`
- 이벤트 판정 로직:
  - `app/server_event_processor.py`

### 클라이언트

- Flutter 앱: `safety_monitor_client/`
- 내장 Python 백엔드: `safety_monitor_client/embedded_backend/`
- 영상 원본 접근과 객체 탐지를 담당

### 뷰어

- Flutter 앱: `safety_monitor_viewer/`
- 서버 API와 서버 프리뷰 스트림만 사용

## 데이터 흐름

### 1. 소스 등록

- 클라이언트가 영상 파일, 카메라, 스트림을 등록
- 서버가 `sources`에 저장

### 2. 로컬 탐지

- 클라이언트가 원본 소스를 열고 객체 탐지 수행
- 프리뷰 프레임 생성
- 프레임 탐지 결과 생성
- 상태 heartbeat 생성

### 3. 서버 저장 및 이벤트 판정

- 서버가 소스 상태와 프레임 탐지 결과 저장
- 서버가 `rule_config`를 기준으로 이벤트 판정
- 이벤트를 `events`에 저장
- 이벤트 클립은 서버에 업로드되어 이벤트와 연결

### 4. 뷰어 조회

- 뷰어는 서버 프리뷰 스트림 확인
- 소스 상태 확인
- 이벤트 로그와 상세 조회
- 이벤트 클립 재생

## 현재 설계 원칙

- 원본 영상 소유권은 클라이언트에 둡니다.
- 중앙 이벤트 판정과 저장은 서버에 둡니다.
- 뷰어는 읽기 전용으로 유지합니다.
- 소스별 룰 변경은 클라이언트에서만 합니다.

## 멀티소스

- 한 클라이언트가 여러 소스를 동시에 소유할 수 있습니다.
- 서버는 여러 클라이언트의 소스를 함께 저장하고 조회하게 해 줍니다.
- 뷰어는 여러 클라이언트의 소스를 한 화면에서 모니터링할 수 있습니다.

## 현재 한계

- 원본 영상 자체를 서버가 직접 재생하는 구조는 아닙니다.
- 뷰어는 서버 프리뷰 스트림을 보는 모니터링 콘솔입니다.
- DB는 SQLite 기반이라 대규모 동시 writer 환경에는 한계가 있습니다.
